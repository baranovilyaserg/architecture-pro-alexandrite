# Выбор и настройка мониторинга в системе

Технический план внедрения мониторинга системы «Александрит». 

## Мотивация

- Устранить «слепые зоны»: сейчас нет метрик, алёртов и понятных дашбордов — команда узнаёт о проблемах по жалобам клиентов или вручную.
- MES выполняет тяжёлые расчёты (2–30 минут). Без метрик невозможно контролировать очередь задач, SLA и очередь повторных запусков.
- Быстрое обнаружение деградации (DB, очереди, сервисы) позволит сократить время простоя и ускорить реакцию поддержки.
 - Отслеживать бизнес‑поведение: мониторинг позволяет видеть, какие функции используют клиенты, а какие — нет. Это помогает выявлять неиспользуемый функционал, оптимизировать приоритеты разработки, перераспределять ресурсы и экономить затраты на поддержку/развитие.

## Выбранный подход

Рекомендую комбинированный подход:

- RED (Rate, Errors, Duration) — для frontend/backend HTTP API и основных user-facing flows (онлайн-магазин, CRM API).
- «Четыре золотых сигнала» (Latency, Traffic, Errors, Saturation) — для инфраструктурных компонентов (MES, БД, очереди).

Причина: RED даёт быстрый сигнал о пользовательском опыте; Golden Signals покрывают инфраструктуру и насыщенность ресурсов, что критично для MES.

## Какие метрики собирать

Общие метки: `service`, `env` (dev/release/prod), `instance`, `region`, `queue`.

1) HTTP / API (Java Spring Boot, C#):
   - rate: `http_server_requests_total{service,method,uri,status}`
   - latency: `http_server_request_duration_seconds_bucket{le}` (p50/p95/p99)
   - errors: `http_server_errors_total`

2) MES-specific (важно для долгих задач):
   - время расчёта: `mes_calculation_duration_seconds` (histogram/summary)
   - p95/p99, median, count
   - очередь расчётов: `mes_job_queue_length{queue}`
   - успех/ошибка по job: `mes_job_processed_total{status="success|failure"}`

3) RabbitMQ / очереди:
   - `rabbitmq_queue_messages_ready{queue}`
   - `rabbitmq_queue_messages_unacknowledged{queue}`
   - `rabbitmq_queue_consumers{queue}`

4) Базы данных (Yandex Managed):
   - connection usage: `db_connections_used{db}`
   - replica lag: `postgres_replica_lag_seconds` (если есть реплики)
   - slow queries: инструментировать или экспортировать через pg_stat_statements

5) Инфраструктура (EC2, контейнеры):
   - cpu: `node_cpu_seconds_total` / `process_cpu_seconds_total`
   - memory: `node_memory_MemAvailable_bytes`, `process_resident_memory_bytes`
   - disk: `node_filesystem_avail_bytes`

6) Business metrics (по заказам):
   - `orders_created_total`, `orders_submitted_total`, `orders_price_calculated_total`, `orders_pending_long_processing{age_bucket}`

## Ярлыки (labels)

- `service` — e.g. `shop`, `crm`, `mes`, `rabbitmq`, `db`.
- `env` — `dev`, `release`, `prod`.
- `instance` — инстанс/контейнер id.
- `queue` — имя очереди (для RabbitMQ и job queues).
- Для трассировки/лога: `order_id`.

## План действий (high level)

1. PoC (1–2 недели)
   - Развернуть Prometheus + Grafana + Alertmanager в dev.
   - Интегрировать экспорт данных.
   - Создать базовые дашборды: Overview, MES jobs, RabbitMQ, DB health, API health.

2. Instrumentation (2–4 недели)
   - Добавить метрики RED во все backend-сервисы.
   - Экспортировать MES job metrics и p95/p99 расчётов.

3. Алертинг и runbooks (1 неделя)
   - Описать runbook для ключевых алёртов (MES backlog, p99 > SLA, DB replica lag, rabbitmq unacked messages).
   - Настроить маршрутизацию алёртов (Alertmanager) — кто получает, через какой канал (Slack/Email/ticket).

4. Повышение зрелости (после PoC)
   - Настроить долгосрочное хранение метрик (TSDB retention), добавить графы для capacity planning.
   - Постепенно покрыть frontend RUM (опционально) для понимания real-user latency.

## Примеры порогов насыщенности и действий (saturation)

- MES job queue length > 50 (5m): создать тикет + оповестить on-call → запустить дополнительный worker / масштабировать MES.
- mes_calculation_p95 > 300s (5m): назначить priority, проверить traces (Jaeger), возможный rollbac.
- rabbitmq_unacked > 1000 (10m): остановить приём новых задач, разослать оповещение, исследовать consumer failures.
- db_connections_used / max > 0.85 (5m): увеличить пул и/или открыть read-replicas; создать тикет DBA.
- node_cpu > 85% (10m): autoscale (если доступно) или поднять инстансы вручную.
