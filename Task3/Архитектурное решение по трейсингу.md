# Архитектурное решение по трейсингу

Внедрение распределённого трейсинга системы «Александрит». Цель — дать команде возможность отследить жизненный путь заказа (order) через все компоненты, быстро находить точки зависания и причины потери сообщений.

## Мотивация

- Заказы часто «зависают» или оказываются в непонятном состоянии — сейчас потерянные сообщения и долгие расчёты MES трудно кореллировать.
- Трейсинг даёт возможность восстановить end-to-end картину по конкретному заказу: какие сервисы были вызваны, какие операции заняли время, где возникли ошибки/ретраи.
- Бизнес-выгоды: снижение MTTR, повышение надёжности SLA по срокам расчёта цены, уменьшение количества жалоб от клиентов и API-партнёров.

Влияемые метрики (технические и бизнес):

- p95/p99 времени расчёта (mes_calculation_duration)
- доля заказов, у которых нет статуса PRICE_CALCULATED в течение SLA (например, 30 минут)
- количество повторных попыток/ретраев по job
- время между SUBMITTED и PRICE_CALCULATED (end-to-end)
- количество потерянных сообщений (RabbitMQ unacked/ready over threshold)

## Область покрытия (scope)

Покрыть трейсингом следует следующие компоненты (порядок важности):

1. MES (backend C#) — критично: здесь происходят долгие расчёты.
2. CRM (backend Java Spring Boot) — создание/обновление статусов заказа.
3. Онлайн-магазин (frontend + backend) — генерация и отправка заказа.
4. RabbitMQ — промежуточный брокер сообщений (producer/consumer spans, ingest/ack).
5. Инфраструктурные точки: база данных (вызовы, долгие запросы), внешние интеграции (транспорт, API партнёров).

## Какие данные должны попадать в трейсинг (список полей)

Обязательные атрибуты:

- trace_id, span_id
- parent_span_id (если есть)
- timestamp (start/end)
- service — имя сервиса (shop/crm/mes)
- env — `dev|release|prod`
- order_id — уникальный идентификатор заказа
- operation — короткое имя операции (e.g. `submit_order`, `enqueue_job`, `calculate_price`, `update_status`)
- status — internal status/result (e.g. `ok`, `error`, `timeout`)
- duration_ms — время выполнения операции в миллисекундах
- poly_count — число полигонов 3D-модели (важно для MES)
- job_id / task_id — идентификатор фоновой задачи в MES
- retry_count — число попыток обработки
- queue_name — для span'ов, связанных с RabbitMQ
- error.message / error.type (при ошибке)

Дополнительно (опционально): request_id, user_id(с учетом безопасности).

Примеры span-последовательности при обработке заказа:

1. shop:submit_order (HTTP span) — включает order_id, user_id
2. shop:publish_order_to_queue (producer span) — включает queue_name
3. rabbitmq:enqueue (broker internal span)
4. mes:consume_job (consumer span) — job_id, poly_count
5. mes:calculate_price (worker span) — duration, poly_count, status
6. mes:publish_status (producer span)
7. crm:update_order_status (HTTP span)

## Предлагаемое решение (технологии и архитектура)

Рекомендую использовать OpenTelemetry как единый стандарт для трассировки и следующие компоненты:

- Инструментация сервисов: OpenTelemetry SDK
- Collector: OpenTelemetry Collector — собирает, обогащает и экспортирует трассы.
- Storage/Backend: Jaeger для хранения и просмотра трейсов. Jaeger проще для PoC, Tempo лучше масштабируется и интегрируется в Grafana.
- UI: Jaeger UI или Grafana (Trace view в Grafana + Tempo) — интеграция с Grafana удобна для объединения метрик, логов и трейсов.

Архитектурная [схема](jewerly_c4_model_with_tracing.drawio) :

shop/crm/mes (instrumented) -> OTEL Collector -> (Jaeger/Tempo) storage
                                         \-> Prometheus (metrics) -> Grafana
                                         \-> Loki/OpenSearch (logs) -> Kibana/Grafana

## Автоматический мониторинг и алертинг на основе трейсинга

Можно реализовать следующие автоматические проверки/алерты:

- End-to-end SLA breach: если между SUBMITTED и PRICE_CALCULATED прошло > 30 минут → alert (с основным trace_id).
- Частые ретраи: если order/job имеет retry_count > N за короткий период → alert.
- Обнаружение «зависших» spans: если span `mes:calculate_price` открыт > X минут → alert + link to trace.
- Потеря сообщений: если для отправленного producer span нет соответствующего consumer span в течение T минут → alert.

Техническая реализация:

- Использовать Trace Analytics (если хранится в backend) или экспортировать агрегаты в Prometheus (например, `orders_with_no_consumer_total{...}`) и алертить через Alertmanager.
- Для alert'ов включать ссылку на trace URL (Jaeger/Grafana) и order_id в описании.

## Компромиссы и ограничения

- Полноценный трейсинг может увеличить нагрузку и объём хранимых данных — необходимо планировать retention/стоимость хранения.
- Проприетарные/третьесторонние компоненты могут не поддерживать OpenTelemetry — придётся использовать адаптеры/плагин или логирование для корелляции.
- Логи с order_id/PII должны быть защищены; нельзя вставлять чувствительные данные в публичные трейсы/метрики.

## Безопасность и доступ

- Доступ к UI (Jaeger/Grafana/Kibana) должен быть за VPN/внутренней сетью или через SSO (LDAP/OAuth). Роли: Support, Developer, Admin.
- Политика хранения чувствительных данных: order_id — хранить, но с ограниченным доступом; PII — не включать в трейсы/метрики.
