# Архитектурное решение по логированию

Решение по сбору, хранению и анализу логов для системы «Александрит». Цель — сократить время расследования инцидентов, обеспечить корреляцию логов с трейcами/метриками и дать оперативные сигналы поддержки.

## Мотивация

- Быстрая диагностика: сейчас инциденты разбирают по словам клиентов — это долго и ненадёжно. Логи дадут источник истины.
- Корреляция: связка логов + трейсов (trace_id) + метрик ускорит поиск root-cause (MTTR уменьшится).
- Бизнес‑метрики, которые улучшатся:
  - Среднее время расследования инцидента (MTTR).
  - Доля инцидентов, обнаруженных автоматически (alerting) vs вручную.
  - Время до восстановления SLA для обработки заказа (SUBMITTED→PRICE_CALCULATED).
  - Количество жалоб клиентов на «потерянные» заказы.

## Область покрытия и приоритеты (что логировать в первую очередь)

Приоритеты (первые 90 дней):

1. MES (C#, backend) — критично: долгие расчёты и высокая нагрузка; нужно логировать job lifecycle, ошибки расчёта, входные параметры (poly_count) и retry.
2. RabbitMQ (broker + consumers/producers spans) — логировать publish/consume/ack/nack и задержки в очередях.
3. CRM (Java Spring Boot) — логировать изменения статусов заказов (MANUFACTURING_APPROVED, CLOSED), входящие API и consumer flows.
4. Онлайн-магазин (backend + frontend) — логирование событий создания/отправки заказа; фронтенд — опционально RUM/errors для пользователя.

Причина: MES и очереди — источник большинства задержек/потерь; CRM — точка интеграции с бизнес-процессом и UI поддержки.

## Что логировать — набор записей (уровень INFO обязательный)

Формат: JSON-лог (одна JSON-объектная строка) — удобство парсинга и индексации.

Минимальные поля (обязательные для всех логов):

- timestamp (ISO8601)
- level (INFO/WARN/ERROR/DEBUG)
- service (shop/crm/mes/rabbitmq)
- env (dev/release/prod)
- instance (host or container id)
- trace_id (если доступен)
- span_id (если доступен)
- request_id / correlation_id
- message — краткое описание
- ctx — объект с дополнительными полями (order_id, user_id*, job_id, queue_name, poly_count, retry_count)

Обязательные логи уровня INFO (примеры событий):

- Создание заказа: user, order_id, items_count, total_price, timestamp.
- FILE_UPLOADED: order_id, filename, poly_count (если доступен), size.
- SUBMITTED: order_id, user_id, timestamp.
- Publish в очередь (producer): service, order_id, queue_name, message_id.
- Consume job (consumer start): job_id, order_id, poly_count, timestamp.
- Job завершён/неуспех: job_id, order_id, duration_ms, status, error.type/message (если ошибка).
- Изменение статуса заказа в CRM: order_id, old_status, new_status, actor.
- Внешние интеграции (API partners): request/response code, latency, partner_id.

Уровни логирования и правила применения:

- INFO — нормальные бизнес-события и переходы состояний (см. список выше).
- WARN — нестандартные, но не блокирующие ситуации: долгие запросы p95 > threshold, временные ошибки внешних API, снижение числа consumers.
- ERROR — падения, исключения, места, где нужна ручная проверка/возврат средств; лог должен содержать stacktrace и контекст.
- DEBUG — детальные логи только для локальной отладки или по запросу (не хранить в prod постоянно).

Правило: не логировать PII (полные имена, номера телефонов, платежные реквизиты). Хранить user_id/order_id — можно, но доступ к индексам с полями order_id должен быть ограничен.

## Предлагаемое техническое решение (архитектура)

Сбор → Корреляция (trace_id) → Хранение → Анализ (единое UI)

Единая наблюдаемость на базе Prometheus + Grafana + Loki + OpenTelemetry:

- метрики (Prometheus) для RED/Golden Signals и алёртинга;
- трейсы (OpenTelemetry Collector -> Jaeger/Tempo) для end-to-end анализа и root-cause;
- логи (Loki/promtail) в структурированном JSON и быстрый поиск через LogQL в Grafana;
- единое отображение и корреляцию в Grafana (метрики + логи + трейсы).

Компоненты и роль:

- OpenTelemetry SDK в сервисах (Java/C#/JS): генерирует трейсы и добавляет `trace_id` в логи/attributes.
- OTEL Collector: собирает трейсы/метрики (OTLP), экспортирует трейсы в Jaeger/Tempo, метрики в Prometheus remote write (или напрямую в Prometheus via exposition).
- Prometheus: собирает метрики (scrape) от сервисов и Collector; хранит TSDB и служит источником для алёртов.
- Loki + promtail: собирают структурированные JSON-логи; promtail делает парсинг и добавляет лейблы (service, env, instance, order_id как label — осторожно).
- Grafana: единое UI для дашбордов, Explore (логов/трейсов) и ссылок на trace view.

Почему:
- Быстро собрать PoC: Prometheus + Grafana + Loki легко развернуть вместе (Helm/docker-compose/Minikube).
- Хорошая корреляция: Grafana поддерживает логов-трейс-метрик correlation (Trace to logs, logs to traces).
- Стоимость и масштабируемость: Loki дешевле для логов по сравнению с полнотекстовыми индексами, Prometheus — де-факто стандарт для метрик.

## Критерии выбора технологии (примерная таблица)

Критерии: лицензия, масштабируемость, полнотекстовый поиск, стоимость хранения, интеграция с Grafana/Jaeger, простота эксплуатации.

- OpenSearch: Apache2, хорош в полнотекстовом поиске, зрелые инструменты, средняя сложность эксплуатации.
- Elasticsearch (Elastic License): мощный, но лицензионные ограничения; платные фичи.
- Loki: простая интеграция с Grafana, дешёвле, label-based поиск → хуже для free-text.

Вывод: рекомендую OpenSearch для продакшн при необходимости мощного поиска; Loki как быстрый и экономный PoC/альтернатива.
